# Fechamento — operacao-e-backup

## O que foi entregue

Log estruturado com redação central e correlação por requisição (`src/lib/log.ts`, `src/proxy.ts`), erro com código de referência e sem pilha (páginas, rotas e ações), configuração validada no start de produção (`validarAmbiente`), `GET /api/saude` e a tela Configurações > Sistema, o backup consistente (`src/lib/backup.ts`, `npm run backup`, geração, lista e download na tela), a restauração só por linha de comando (`src/lib/restauracao.ts`, `npm run restore`) com o teste que a prova (PR-20), o desligamento limpo, o comando do primeiro administrador, `Dockerfile`, entrypoint, `docker-compose.yml`, o job de CI que constrói a imagem e a documentação operacional (README, `.env.example`). Premissas PR-92 a PR-100; PR-20, PR-21 e PR-24 realizadas.

## Decisão principal

O backup é um arquivo só, feito pela API de backup online do SQLite (preserva rowid e o índice de busca), com manifesto e SHA-256 por parte, sem temporários e sem a `ENCRYPTION_KEY`. A restauração não é oferecida pelo navegador: ela troca o banco sob um servidor de pé, por isso é um comando com o servidor parado, que valida tudo antes de tocar, guarda uma cópia `pre-restauracao-<data>`, desfaz se algo falhar e registra a auditoria `restauracao` no banco restaurado.

## Risco residual

A `ENCRYPTION_KEY` precisa ser guardada em separado, ou as chaves cifradas não decifram depois de restaurar. O sistema só mantém a cópia local do backup (PEND-09). A imagem foi verificada em arm64 na máquina de desenvolvimento. A verificação visual não usou celular real nem leitor de tela.
